# Hanword 2024 compatibility matrix

**Status meanings**

- **구현 완료**: connected to the active document model and exercised by an automated model/export/reopen test for the stated scope.
- **부분 구현**: some paths work, but coverage, formats, selection shapes, UI integration, or platform validation is incomplete.
- **미구현**: no working Hanul command exists today.
- **검증 불가**: neither direct UI evidence nor a reliable primary source was available in this task.

The matrix records verified scope, not a claim of full Hanword compatibility. GUI/REA binary inspection is not a substitute for RHWP's file-format fidelity checks.

**Validation for independent table editing (2026-10-15):** Windows 11 `npm run build` and the full 81-test frontend suite passed. Ubuntu 26.04 WSL2 isolated-copy build and 81 tests passed on Node 22.22.1 (locked packages emit engine-version warnings requesting 22.22.2); the Linux Tauri backend also passes `cargo check`. Windows Hanul GUI confirmed table insertion, cell text entry, Tab navigation, row/column insertion, column deletion, merge/split, and applying a 150 mm table width. A saved HWP opened in installed Hanword 2024 and visibly retained the cell text and merged grid. Generated HWP/HWPX fixtures cover independent import, spans, styles and dimensions, edit, zero-reported-loss export, and reopen, including tables flowing over three pages. Linux table GUI/IME, HWPX open in Hanword 2024, row deletion in the GUI, and physical input-to-screen timing were not verified.

**Validation for independent picture/shape support (2026-10-15):** Windows 11 and Ubuntu 26.04 WSL2 each passed `npm run build` and all 87 frontend tests. Windows `cargo check --workspace --locked` and Ubuntu 26.04 WSL2 `cargo check --workspace --locked` also passed. Generated HWPX round-trip tests cover image bytes, picture aspect-preserving resize, rectangle, ellipse, editable text-box content, Undo/Redo, and re-edit after reopening. Real Hanword 2024 checks opened a plain-text HWP/HWPX, rectangle-only HWP, picture-only HWP, and an object-rich HWPX. An earlier Hanword GUI attempt with a separate text-box HWP and a picture + text-box HWP showed “파일이 손상되었습니다”; this is not a general result for all candidates: a later isolated Korean textbox diagnostic HWP opened and rendered in Hanword's normal UI. The picture + textbox case remains unverified with a controlled fixture. Hanul's independent-engine serializer now refuses HWP serialization when a text box exists and directs the user to HWPX, which was accepted by Hanword with picture/text-box content visible. HWPX text-box acceptance does not validate every layout property. Windows GUI verified independent-engine rectangle insert/move/resize/delete/undo/redo, ellipse insertion, text-box editing and visible text, and picture insert/move/resize/delete/undo/redo. GUI screenshots rendered normally; the earlier black capture was not reproduced. Linux WSLg object GUI/IME and actual frame/input timing were not run. Synthetic object engine timings are recorded in `docs/performance/editing-benchmark.md`; React/WebKit paint and physical frame timing remain unmeasured.

**Validation for HWP textbox storage and safe save (2026-10-15):** Raw inspection of the previously Hanword-rejected Hanul HWP found `HWPTAG_SHAPE_COMPONENT` (`0x04C`) with `flip=0x00080000`; the textbox list header and nested paragraph records were present. The HWPX-to-HWP adapter candidate had `flip=0x01000000`. Hancom's [HWP 5.0 revision 1.3 format specification](https://cdn.hancom.com/link/docs/%ED%95%9C%EA%B8%80%EB%AC%B8%EC%84%9C%ED%8C%8C%EC%9D%BC%ED%98%95%EC%8B%9D_5.0_revision1.3.pdf) documents drawing-object attributes and textbox text/list records (section 4.3.9.2, tables 81, 83, and 90), but does not define these upper `flip` values. RHWP v0.8.7's `src/parser/hwpx/section.rs` comments that Hancom 2020 saved HWPX text-box drawings with `0x01000000`; this is upstream observed behavior, not a normative bit definition. Because the available evidence conflicts with treating `0x00080000` and `0x01000000` as a required combined value, Hanul does not rewrite these bits. The UI-level independent-engine HWP textbox guard remains, and the Tauri save validator now rejects any HWP containing text boxes before replacing the destination; HWPX remains available. A generated HWPX-adapter candidate reopens in RHWP with textbox and text intact, but this is not Hanword compatibility evidence. The Computer Use helper returned `GetCursorPos` access denied during the attempted Hanword check. Desktop saves stage beside the destination, parse/reopen the staged document, check the format/page structure, then atomically replace the destination; validation failures preserve the original. Windows validation: frontend 88 tests, build, Rust 11 tests, `cargo fmt --check`, and workspace check passed. Ubuntu 26.04 WSL2 isolated-copy validation: frontend 88 tests and build, Rust 11 tests, and workspace check passed. Linux GUI/IME remains unverified. A later normal-UI Hanword check opened and rendered the post-margin-fix isolated Korean textbox diagnostic candidate; app save, edit/save/reopen, and mixed cases remain unverified.

**Earlier HWP textbox follow-up before the GUI edit/save checks (2026-10-15):** A Hanword 2024 COM automation-created Korean textbox HWP reopened successfully through the same API, and its text was read back. A Hanul one-textbox Korean diagnostic candidate also opened and returned its text. Its SHA-256 is byte-identical to the candidate previously reported as damaged, so that earlier rejection is not reproducible for the same bytes. The native file has `flip=0x01080000`; the candidate has `flip=0x01000000`, demonstrating that this difference alone is not a confirmed damage cause. Field sizes and geometry differ; see [the controlled-scope record comparison](../research/hwp-textbox-compatibility.md). The comparison also found a separate 2 mm textbox-margin loss in the Hanul candidate path, now fixed by serializing all four `tbMargin*` values and covered by an RHWP reparse test (2 mm → 567 HU). The post-margin-fix diagnostic candidate was opened with Hanword's normal file-open UI and its Korean text box visibly rendered. This verifies basic open/display for that isolated candidate only; the normal app-save path, Hanword edit/save/reopen, and mixed-content/resized cases remain unverified. No HWP serialization cause is confirmed; the user's HWP save guard and backend validation remain enabled.

**Validation of textbox-margin follow-up (2026-10-15):** Windows `npm test -- --reporter=dot` passed 88/88, `npm run build` passed, `cargo test --workspace --locked` passed 11/11, `cargo fmt --check` passed, and `git diff --check` passed. Ubuntu 26.04 WSL2 isolated-copy `npm test` passed 88/88, `npm run build` passed, and `cargo test --workspace --locked` passed 11/11. Linux GUI/IME was not run. After this test run, the post-fix isolated Korean textbox diagnostic candidate was opened and visibly rendered through Hanword's normal file-open UI; this was not an app-save or edit/save/reopen test.

**Hanword 2024 textbox candidate verification (2026-10-15):** The three requested candidates were found in `%LOCALAPPDATA%\HanulValidation20261015` rather than the specified `Temp` subdirectory; original files were hash-checked before/after and remained unchanged. Separate copies were opened in Hanword 2024. The body + one textbox candidate and the resized/moved single-textbox candidate opened without a damage warning, displayed Korean text, allowed textbox editing, saved under new names, and reopened with the edit intact. Hanword properties confirmed 50×24 mm at 77.24/20.00 mm with 2 mm inner margins for the body candidate, and 80×35 mm at 37/28 mm with 2 mm inner margins for the resized candidate. The picture + textbox candidate also opened and allowed textbox edit/save/reopen, but the picture could not be visually verified: it overlaps the white textbox at the same paper position and RHWP reports about 98.8% crop. Thus only the exact body+single-textbox diagnostic structure gets a golden structural fixture; this does not exercise the normal app save path. That path and Tauri validation still block all HWP text boxes, and mixed picture/shape documents remain blocked. No HWP serializer change or save-guard relaxation was made. See [the detailed GUI evidence](../research/hwp-textbox-compatibility.md).

**Golden regression and platform run (2026-10-15):** Windows passed all 89 frontend tests, `npm run build`, 11 Rust workspace tests, and `cargo fmt --check`. Ubuntu 26.04 WSL2 passed all 89 frontend tests and `npm run build` from an isolated Linux copy of the current frontend sources; Node 22.22.1 emitted engine warnings for packages requesting 22.22.2. A separate Linux Rust test attempt could not complete because WSL `/tmp` had only 56 KB free (`No space left on device`); the run’s temporary 339 MB copy was removed, leaving the pre-existing `.linux-validation-objects-20261015` untouched. No Linux GUI/Hanword test was attempted.
