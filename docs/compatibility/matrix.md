# Hanword 2024 compatibility matrix

**Status meanings**

- **구현 완료**: connected to the active document model and exercised by an automated model/export/reopen test for the stated scope.
- **부분 구현**: some paths work, but coverage, formats, selection shapes, UI integration, or platform validation is incomplete.
- **미구현**: no working Hanul command exists today.
- **검증 불가**: neither direct UI evidence nor a reliable primary source was available in this task.

The matrix records verified scope, not a claim of full Hanword compatibility. GUI/REA binary inspection is not a substitute for RHWP's file-format fidelity checks.

**Validation for independent table editing (2026-10-15):** Windows 11 `npm run build` and the full 81-test frontend suite passed. Ubuntu 26.04 WSL2 isolated-copy build and 81 tests passed on Node 22.22.1 (locked packages emit engine-version warnings requesting 22.22.2); the Linux Tauri backend also passes `cargo check`. Windows Hanul GUI confirmed table insertion, cell text entry, Tab navigation, row/column insertion, column deletion, merge/split, and applying a 150 mm table width. A saved HWP opened in installed Hanword 2024 and visibly retained the cell text and merged grid. Generated HWP/HWPX fixtures cover independent import, spans, styles and dimensions, edit, zero-reported-loss export, and reopen, including tables flowing over three pages. Linux table GUI/IME, HWPX open in Hanword 2024, row deletion in the GUI, and physical input-to-screen timing were not verified.

**Validation for independent picture/shape support (2026-10-15):** Windows 11 and Ubuntu 26.04 WSL2 each passed `npm run build` and all 87 frontend tests. Windows `cargo check --workspace --locked` and Ubuntu 26.04 WSL2 `cargo check --workspace --locked` also passed. Generated HWPX round-trip tests cover image bytes, picture aspect-preserving resize, rectangle, ellipse, editable text-box content, Undo/Redo, and re-edit after reopening. Real Hanword 2024 checks opened a plain-text HWP/HWPX, rectangle-only HWP, picture-only HWP, and an object-rich HWPX. A text-box-only HWP and a HWP containing picture + text box both triggered Hanword's “파일이 손상되었습니다” error. Hanul's independent-engine serializer now refuses HWP serialization when a text box exists and directs the user to HWPX, which was accepted by Hanword with picture/text-box content visible. HWPX text-box acceptance does not validate every layout property. Windows GUI verified independent-engine rectangle insert/move/resize/delete/undo/redo, ellipse insertion, text-box editing and visible text, and picture insert/move/resize/delete/undo/redo. GUI screenshots rendered normally; the earlier black capture was not reproduced. Linux WSLg object GUI/IME and actual frame/input timing were not run. Synthetic object engine timings are recorded in `docs/performance/editing-benchmark.md`; React/WebKit paint and physical frame timing remain unmeasured.

| Headers/footers | 부분 구현 | A page-scope dialog edits/deletes a single plain-text paragraph for current page target, both, even, or odd pages; page-number/total-pages/file-name markers can be inserted. These three markers are control characters rather than complete field records/references; RHWP drops them from HWP/HWPX output and re-open does not restore them. Hanul now checks every header/footer paragraph, verifies the same paragraph after export/reopen, and puts the exact field/scope/paragraph in the existing explicit loss-confirmation dialog. Automated regression covers all three markers in both formats. This warns before a lossy save; it does not preserve the field record. Multi-paragraph and field-aware editing are not supported. |

Every save path keeps the original HWP or HWPX source format and checks RHWP's content-loss report. A zero-count report means the library reported no known export loss; it is not proof that all Hancom features are fully preserved.

Hancom binary observations do not establish that Hanul can read or write a feature. Format support remains tied to RHWP behavior and Hanul round-trip tests.
