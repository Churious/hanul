# Hanword 2024 compatibility matrix

**Status meanings**

- **구현 완료**: connected to the active document model and exercised by an automated model/export/reopen test for the stated scope.
- **부분 구현**: some paths work, but coverage, formats, selection shapes, UI integration, or platform validation is incomplete.
- **미구현**: no working Hanul command exists today.
- **검증 불가**: neither direct UI evidence nor a reliable primary source was available in this task.

The matrix records verified scope, not a claim of full Hanword compatibility. GUI/REA binary inspection is not a substitute for RHWP's file-format fidelity checks.

### V1-01 save compatibility baseline (2026-10-15)

Save eligibility now returns `SUPPORTED`, `UNSUPPORTED`, `LOSSY`, or `UNKNOWN` with a stable reason code and affected element counts. The report identifies the format, source engine (`hanul-text` or `rhwp-compat`), validator, and its `internal-structure` scope; `SUPPORTED` is not a claim of Hanword interoperability. UI preflight and the Tauri staged-file/atomic-commit gate use matching policy rules, covered by corresponding TypeScript and Rust profile matrices. RHWP-backed text boxes remain blocked for HWP; Hanul's previously Hanword-verified single rectangular, one-paragraph text box profile remains allowed. Unknown controls, unverified multi-section documents, unknown range tags, HWPX multi-paragraph/multiple/nested text boxes, and unsupported controls are blocked. Serializer-reported losses remain `LOSSY` and require explicit user confirmation; a structural `UNSUPPORTED`/`UNKNOWN` result cannot be overridden by that confirmation. Errors name affected element kinds/counts. Failed validation leaves the destination bytes unchanged.

The automated structure corpus reuses the checked-in Hanword-verified textbox HWP Golden and creates disposable HWP/HWPX byte fixtures in existing engine tests for plain/formatted text, merged cells, pictures, rectangles/ellipses, text boxes, mixed object HWPX, header/footer text, field-loss reporting, and page breaks. The policy matrix also covers multiple sections and unknown controls as explicit blocks. No Hanword GUI validation was performed as part of V1-01; the prior single-textbox Golden evidence is the only external Hanword claim. The test corpus verifies RHWP reparse and semantic fields asserted by each test, not universal binary fidelity.

V1-01 verification: Windows passed 100/100 frontend tests, `npm run build`, 16 Rust tests (1 ignored), and `cargo fmt --check`. Ubuntu 26.04 WSL passed the same 100 frontend tests, build, and 16 Rust tests (1 ignored). WSL's installed Rust toolchain has no `rustfmt`, so Linux formatting was not checked. These are automated model/file tests; no GUI, IME, or new Hanword 2024 test was run.

**V1-02a lifecycle follow-up (2026-10-15):** The app now guards asynchronous document loads with a monotonically increasing request generation. Late parse results after a newer request, close, or component teardown are disposed instead of replacing the live document; stale callbacks do not clear the latest loading state. Save/discard/cancel decisions for pending open/close/exit actions share a tested resolver, and Save resumes the requested action only after the existing save pipeline succeeds. Windows frontend tests passed 108/108 and `npm run build` passed; Rust workspace tests passed 16 with 1 ignored. Ubuntu 26.04 WSL2 isolated-copy frontend tests passed 108/108, build passed, and Rust workspace tests passed 16 with 1 ignored. Linux Node 22.22.1 printed engine-version warnings for packages requesting 22.22.2. A Windows Codex in-app browser GUI smoke test created a blank document, typed text, verified the dirty indicator, opened the new-document warning, confirmed Cancel retained the text and dirty state, confirmed Discard opened a clean blank document, and confirmed the Save choice advanced to the pending blank document. The browser download event was not observed, so the output file and reopen were not verified. The existing read-only Document Information dialog displayed its basic fields. This was not a Tauri desktop GUI test: native file dialogs, recent-path reopen, actual HWP/HWPX open/save/reopen, native close prompts, Linux GUI, and Hanword 2024 were not tested. V1-02 and FIL-01/04/09/15 remain partial.

The Tauri backend stages the serialized file in the destination folder, inspects that file, applies the structural policy again during atomic commit, then replaces the destination only after validation. Automated tests cover the Hanword GUI-verified body + one plain rectangular textbox Golden through this commit path, serializer edit/export/reopen and 50×24 mm geometry/2 mm margins. Hanword 2024 opened the actual product serializer + Tauri-commit output without a damage warning; the body and textbox displayed, Korean text was edited, saved to a separate HWP, and the Hanword-saved HWP reopened with the edit. A product-generated resized/moved 80×35 mm output was Hanword-saved and the saved copy was reopened; text and size 80×35 mm were visible. Position and margins in that final reopen were not rechecked. Multi-paragraph text boxes, multiple textboxes, table/picture mixed cases, fields/range tags, nested content, and multiple sections remain blocked. The picture+textbox diagnostic has coincident placement and about 98.8% crop; overlap and crop have not been isolated, so no serializer change was made. HWPX structural policy is unchanged; serializer loss reports remain separate. Windows passed 92 frontend tests, production build, Rust 13 passed/1 ignored, and `cargo fmt --check`. Ubuntu 26.04 WSL2 passed 92 frontend tests, production build, and Rust 13 passed/1 ignored on Node 22.22.1. Linux GUI/IME, ordinary desktop Linux, `cargo fmt --check` there, and a native Linux package build were not verified. Rust output and temporary files reused `HanulLinuxValidation20261015` under the Windows volume because `/tmp` had about 335 MiB free; existing `/tmp` data and validation files were preserved.

**Earlier diagnostic-stage validation before product-scope unblocking (2026-10-15):** Raw inspection of the previously Hanword-rejected Hanul HWP found `HWPTAG_SHAPE_COMPONENT` (`0x04C`) with `flip=0x00080000`; the textbox list header and nested paragraph records were present. The HWPX-to-HWP adapter candidate had `flip=0x01000000`. Hancom's [HWP 5.0 revision 1.3 format specification](https://cdn.hancom.com/link/docs/%ED%95%9C%EA%B8%80%EB%AC%B8%EC%84%9C%ED%8C%8C%EC%9D%BC%ED%98%95%EC%8B%9D_5.0_revision1.3.pdf) documents drawing-object attributes and textbox text/list records (section 4.3.9.2, tables 81, 83, and 90), but does not define these upper `flip` values. RHWP v0.8.7's `src/parser/hwpx/section.rs` comments that Hancom 2020 saved HWPX text-box drawings with `0x01000000`; this is upstream observed behavior, not a normative bit definition. Because the available evidence conflicts with treating `0x00080000` and `0x01000000` as a required combined value, Hanul does not rewrite these bits. At that stage, the UI guard and Tauri validator rejected every HWP containing text boxes; HWPX remained available. A generated HWPX-adapter candidate reopened in RHWP with textbox and text intact, but this was not Hanword compatibility evidence. Desktop saves stage beside the destination, parse/reopen the staged document, check the format/page structure, then atomically replace the destination; validation failures preserve the original. Windows validation at that time: frontend 88 tests, build, Rust 11 tests, `cargo fmt --check`, and workspace check passed. Ubuntu 26.04 WSL2 isolated-copy validation: frontend 88 tests and build, Rust 11 tests, and workspace check passed. Linux GUI/IME was unverified. Subsequent product-path evidence is recorded above.

**HWP textbox product-save scope (2026-10-15):** A structured compatibility report now replaces the scattered textbox Boolean checks. The session adapter reports HWP/HWPX, section/paragraph/table/object counts, textbox paragraph count/shape, unsupported properties, nested content, fields/range tags, and stable issue codes. The Tauri backend inspects the serialized file after it has been staged beside the destination, then re-parses and applies the same structural policy again at atomic commit. A single section with a plain rectangular textbox and one inner paragraph remains the only textbox structure enabled for HWP; multiple textboxes, multiple sections, multi-paragraph or nested content, fields/range tags, and table/image/object mixtures remain blocked. Other export losses continue through the explicit serializer loss report; the structural report does not claim full format fidelity.

**Validation of textbox-margin follow-up (2026-10-15):** Windows `npm test -- --reporter=dot` passed 88/88, `npm run build` passed, `cargo test --workspace --locked` passed 11/11, `cargo fmt --check` passed, and `git diff --check` passed.
